Motion spec

Every demo below is running code, not a recording, and none of it starts on its own — tap a control to play it, the same rule the artboards follow. Numbers are the real durations; the slow-motion tweak scales them for review.

The verdict: no library

0 bytes added · 3 platform primitives

Edicola has no build step and admits runtime libraries only from esm.sh, pinned, one choke point each. A motion library would be the fourth such import, cached by the service worker, loaded on every cold start — to do what the platform now does natively. The three primitives below cover every animation in this spec.

01 CSS transitions on the existing tokens

State changes that lit-html already re-renders: chips, buttons, the progress bar. --dur-fast and --ease ship already; twelve rules in styles.css use them.

02 Web Animations API with linear() springs

Anything that starts from where the finger landed: the Story opening out of its ring, the Save pop. el.animate() returns a handle you can reverse or re-target mid-flight, which is the whole of what a spring library sells.

03 View Transitions, progressively

List ↔ Feed, and Today → Reader. One document.startViewTransition wrapper in src/render.js; where it is missing the render just happens, as it does today.

Tokens this adds

Four values, appended to the motion group in the bare :root block. Not theme-scoped: motion does not change between dark and light. The two springs are solved once and written out as linear() ramps, so there is no solver at runtime.

Reduced motion is a path, not a switch

styles.css already zeroes every transition-duration under prefers-reduced-motion, which handles primitive 01 and nothing else — a WAAPI animation ignores that rule entirely. So each script reads the query and takes a shorter branch: the Story still opens, it just cross-fades in 120ms instead of growing out of the ring. Toggle it on the demos above with the control by the section heading.

// src/motion.js — the whole module. No dependencies, no exports beyond these three.

/** The reader's preference, read at call time: it can change while the app is open. */
export function prefersReducedMotion() {
  return window.matchMedia('(prefers-reduced-motion: reduce)').matches;
}

/** Read a motion token off :root so JS and CSS never disagree about a duration. */
export function motionToken(name) {
  return getComputedStyle(document.documentElement).getPropertyValue(name).trim();
}

/** Grow `panel` out of `origin`. Returns the Animation so the caller can reverse it. */
export function growFrom(origin, panel, { duration, easing }) {
  if (prefersReducedMotion()) {
    return panel.animate([{ opacity: 0 }, { opacity: 1 }], { duration: 120, fill: 'both' });
  }
  const a = origin.getBoundingClientRect();
  const b = panel.getBoundingClientRect();
  const dx = a.left + a.width / 2 - b.left - b.width / 2;
  const dy = a.top + a.height / 2 - b.top - b.height / 2;
  const from = 'translate(' + dx + 'px,' + dy + 'px)'
    + ' scale(' + a.width / b.width + ',' + a.height / b.height + ')';
  return panel.animate(
    [{ transform: from, borderRadius: 'var(--r-pill)', opacity: 0 },
     { transform: 'none', borderRadius: '0px', opacity: 1 }],
    { duration, easing, fill: 'both' },
  );
}

Verification

Tests cover logic, not motion. Drive headless Chrome over CDP and capture each transition at its midpoint with Animation.setCurrentTime, in both themes.

No ADR is needed to add a file, but the choice not to take a dependency is exactly what docs/adr/ is for. Worth a short one, so the next person proposing a motion library finds the reasoning instead of repeating it.
